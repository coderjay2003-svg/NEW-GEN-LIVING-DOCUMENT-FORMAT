# Module 12 — LDFX Plugin Architecture Specification

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** Module 01, Module 03, Module 04, Module 05, Module 08, Module 09, Module 10, Module 11
**Required By:** final_integration

---

## 1. Purpose

This module defines the complete plugin architecture for the LDFX ecosystem. Plugins are first-class citizens — they extend document capabilities, add new node types, provide custom renderers, integrate external services, and enable domain-specific functionality without modifying the LDFX core.

The plugin system is designed so that a well-written plugin is indistinguishable from a built-in feature from the user's perspective.

---

## 2. Plugin Architecture Principles

- Every plugin executes inside the WASM sandbox (Module 09 §3)
- Plugins declare all capabilities and permissions upfront — no runtime escalation
- Plugins are versioned independently of the LDFX specification
- Plugins may be embedded in the document or loaded from the runtime's plugin registry
- Embedded plugins travel with the document — the document is self-contained
- Plugin APIs are stable across MINOR versions — breaking changes require a MAJOR bump

---

## 3. Plugin Types

| Type | Description |
|---|---|
| `renderer` | Provides rendering for custom node types |
| `editor` | Adds editing capabilities to the LDFX Editor |
| `importer` | Imports content from external formats (PDF, DOCX, etc.) |
| `exporter` | Exports document to external formats |
| `ai_provider` | Provides AI inference capabilities |
| `sync_provider` | Provides cloud synchronization backend |
| `theme` | Provides visual themes and style overrides |
| `tool` | General-purpose document processing tool |

---

## 4. Plugin Package Structure

Each plugin is a self-contained directory inside `plugins/<plugin-id>/`:

```
plugins/com.example.chartplugin/
├── plugin.json          ← plugin manifest (required)
├── main.wasm            ← compiled WASM module (required)
├── assets/              ← plugin-specific assets (optional)
│   └── icon.webp
├── schemas/             ← JSON schemas for custom node types (optional)
│   └── chart_node.json
└── locales/             ← plugin localization strings (optional)
    ├── en.json
    └── fr.json
```

## 5. Plugin Manifest (`plugin.json`)

```json
{
  "schema_version": "1.0.0",
  "id": "com.example.chartplugin",
  "name": "Chart Plugin",
  "description": "Provides interactive chart rendering for LDFX documents",
  "version": "2.1.0",
  "minimum_runtime_version": "1.0.0",
  "maximum_runtime_version": null,
  "type": "renderer",
  "author": {
    "name": "<author name>",
    "email": "<author email>",
    "url": "https://example.com"
  },
  "license": "MIT",
  "homepage": "https://example.com/chartplugin",
  "entry_point": "main.wasm",
  "permissions": [
    "read_all_pages",
    "write_annotations"
  ],
  "network_domains": [],
  "node_types": ["chart"],
  "exports": [
    {
      "name": "render_chart",
      "description": "Renders a chart node to a bitmap surface"
    }
  ],
  "checksum": "sha256:<full-64-hex>",
  "signed": false,
  "signature": null,
  "trust_level": "untrusted",
  "_reserved": {}
}
```

### 5.1 Plugin Manifest Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `schema_version` | string | Yes | Manifest schema version |
| `id` | string | Yes | Reverse domain plugin identifier |
| `name` | string | Yes | Human-readable plugin name |
| `description` | string | Yes | Plugin description |
| `version` | string | Yes | Plugin semantic version |
| `minimum_runtime_version` | string | Yes | Minimum LDFX runtime version required |
| `maximum_runtime_version` | string | No | Maximum compatible runtime version, or `null` |
| `type` | string | Yes | Plugin type from §3 |
| `author` | object | Yes | Author information |
| `license` | string | Yes | SPDX license identifier |
| `homepage` | string | No | Plugin homepage URL |
| `entry_point` | string | Yes | Path to WASM module within plugin directory |
| `permissions` | array | Yes | Required permissions from Module 09 §3.3 |
| `network_domains` | array | No | Allowed network domains (if `network_read`/`network_write` requested) |
| `node_types` | array | No | Custom node types this plugin handles |
| `exports` | array | Yes | Exported WASM functions |
| `checksum` | string | Yes | SHA-256 of the WASM entry point |
| `signed` | boolean | Yes | Whether the plugin is signed |
| `signature` | string | No | Base64-encoded plugin signature |
| `trust_level` | string | Yes | `untrusted`, `signed`, `verified` |
| `_reserved` | object | Yes | Future extension point |

## 6. Plugin Index (`plugins/index.json`)

```json
{
  "schema_version": "1.0.0",
  "plugins": [
    {
      "id": "com.example.chartplugin",
      "version": "2.1.0",
      "path": "plugins/com.example.chartplugin/",
      "required": true,
      "checksum": "sha256:<full-64-hex>"
    }
  ]
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Yes | Must match `plugin.json` `id` |
| `version` | string | Yes | Must match `plugin.json` `version` |
| `path` | string | Yes | Path to plugin directory inside ZIP |
| `required` | boolean | Yes | If `true`, document cannot open without this plugin |
| `checksum` | string | Yes | SHA-256 of the plugin directory (computed as hash of all plugin files) |

## 7. Plugin Runtime API

The LDFX Runtime exposes a stable API to plugins via WASM imports. Plugins call these functions to interact with the document.

### 7.1 Core API (Always Available)

```
ldfx_log(level: i32, message_ptr: i32, message_len: i32)
ldfx_get_page_count() -> i32
ldfx_get_page_id(page_index: i32, out_ptr: i32) -> i32
ldfx_get_node(node_id_ptr: i32, node_id_len: i32, out_ptr: i32) -> i32
ldfx_emit_event(event_type_ptr: i32, event_type_len: i32, data_ptr: i32, data_len: i32)
ldfx_get_locale() -> i32
ldfx_get_runtime_version(out_ptr: i32) -> i32
```

### 7.2 Renderer API (For `renderer` type plugins)

```
ldfx_render_begin(node_id_ptr: i32, node_id_len: i32, surface_ptr: i32) -> i32
ldfx_render_end(surface_ptr: i32)
ldfx_render_text(surface_ptr: i32, text_ptr: i32, text_len: i32, style_ptr: i32)
ldfx_render_image(surface_ptr: i32, asset_id_ptr: i32, asset_id_len: i32, x: f32, y: f32, w: f32, h: f32)
ldfx_render_rect(surface_ptr: i32, x: f32, y: f32, w: f32, h: f32, style_ptr: i32)
```

### 7.3 Permission-Gated API

These functions are only available if the corresponding permission is granted:

| Function | Required Permission |
|---|---|
| `ldfx_read_all_pages(...)` | `read_all_pages` |
| `ldfx_write_annotation(...)` | `write_annotations` |
| `ldfx_network_get(...)` | `network_read` |
| `ldfx_network_post(...)` | `network_write` |
| `ldfx_fs_read(...)` | `filesystem_read` |
| `ldfx_fs_write(...)` | `filesystem_write` |
| `ldfx_ai_infer(...)` | `execute_ai` |

Calling a permission-gated function without the permission returns an error code — it does not crash the sandbox.

## 8. Custom Node Types

Plugins may register custom node types that extend the content model (Module 11 §6).

### 8.1 Custom Node Registration

A plugin registers custom node types by declaring them in `plugin.json` `node_types` and providing a JSON schema in `schemas/<node-type>.json`.

### 8.2 Custom Node Schema Example

```json
{
  "$schema": "https://spec.ldfx.org/schemas/node/1.0.0.json",
  "node_type": "chart",
  "plugin_id": "com.example.chartplugin",
  "fields": {
    "chart_type": {
      "type": "string",
      "required": true,
      "enum": ["bar", "line", "pie", "scatter"]
    },
    "data_asset_id": {
      "type": "string",
      "required": true,
      "description": "UUID of the data asset in assets/data/"
    },
    "title": {
      "type": "string",
      "required": false
    },
    "color_scheme": {
      "type": "string",
      "required": false,
      "default": "default"
    }
  }
}
```

### 8.3 Unknown Node Type Handling

When a runtime encounters a node type it does not recognize and no plugin handles it:
- If the node has a `fallback` field, render the fallback content
- If no fallback, render a placeholder with the node type name
- Log a warning
- Do not fail the document

This ensures forward compatibility — documents with custom nodes degrade gracefully in runtimes without the plugin.

## 9. Plugin Lifecycle

### 9.1 Plugin Loading

1. Runtime reads `plugins/index.json`
2. For each plugin, verify checksum against declared value
3. Load `plugin.json` from plugin directory
4. Verify plugin version compatibility with runtime (Module 07 §6.3)
5. Request user permission for declared permissions
6. If user denies a required permission and plugin is `required: true` → reject document
7. If user denies a permission and plugin is `required: false` → load plugin with reduced capabilities
8. Instantiate WASM module in isolated sandbox
9. Call plugin `init()` export function

### 9.2 Plugin Execution

- Plugin WASM module runs in its own isolated linear memory
- Plugin cannot access other plugins' memory
- Plugin cannot access the host filesystem without permission
- Plugin CPU time is limited per render frame (default: 16ms per frame)
- Plugin memory is limited (default: 256 MB per plugin)

### 9.3 Plugin Unloading

1. Call plugin `cleanup()` export function
2. Release WASM sandbox memory
3. Remove plugin from active plugin registry

## 10. Plugin Trust and Security

### 10.1 Trust Verification

Plugin trust levels are defined in Module 09 §8.1. The runtime enforces:

| Trust Level | Allowed Permissions |
|---|---|
| `untrusted` | Baseline only (no permission-gated capabilities) |
| `signed` | Low and medium risk permissions |
| `verified` | All declared permissions |

### 10.2 Plugin Isolation

- Each plugin runs in a separate WASM instance
- Plugins communicate only through the LDFX event system
- Plugins cannot call each other's WASM functions directly
- Plugin crashes are isolated — one plugin crashing does not affect other plugins or the runtime

### 10.3 Plugin Checksum Verification

Plugin checksums are verified in Stage 3 of validation (Module 08 §4, manifest validation) and again at plugin load time. A checksum mismatch is a fatal error for required plugins.

---

## 11. Plugin Registry

The LDFX Plugin Registry is a curated catalog of verified plugins maintained by the LDFX project.

Registry entries include:
- Plugin ID and version
- Publisher verification status
- Checksum of each version
- Compatibility matrix
- Security audit status

The registry is distributed as a signed JSON file bundled with the runtime and updated periodically. Plugins in the registry receive `verified` trust level automatically.

## 12. Validation Rules

| Rule | Severity | Condition |
|---|---|---|
| `plugins/index.json` missing when plugins declared | Fatal | `has_plugins: true` but no index |
| Plugin directory missing | Fatal | Index references non-existent directory |
| `plugin.json` missing | Fatal | Required file in plugin directory |
| `plugin.json` invalid JSON | Fatal | Parse error |
| Plugin `id` mismatch | Fatal | `plugin.json` id ≠ index id |
| Plugin `version` mismatch | Fatal | `plugin.json` version ≠ index version |
| Plugin checksum mismatch | Fatal | Computed checksum ≠ declared checksum |
| WASM entry point missing | Fatal | `entry_point` file not found |
| Plugin runtime incompatible | Fatal | If `required: true` |
| Plugin runtime incompatible | Warning | If `required: false` |
| Undeclared permission used | Fatal | Plugin calls permission-gated API without declaration |
| Plugin size exceeds limit | Warning | Single plugin > 50 MB |
| Plugin not signed | Info | Trust level is `untrusted` |
| Custom node type missing schema | Warning | Node type declared but no schema file |
