# Module 01 — LDFX Format Identity Specification

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** None
**Required By:** All modules

---

## 1. Official Format Name

| Field | Value |
|---|---|
| Full Name | Living Document Format Extended |
| Short Name | LDFX |
| Abbreviation | LDFX |
| Pronunciation | "el-dee-ef-ex" |

---

## 2. File Extension

| Field | Value |
|---|---|
| Primary Extension | `.ldfx` |
| Case Sensitivity | Always lowercase on all platforms |
| Alternative Extensions | None permitted |
| Legacy Extensions | None |

### 2.1 Naming Conventions

- File names must use only: lowercase letters (`a–z`), digits (`0–9`), hyphens (`-`), and underscores (`_`)
- Spaces are not permitted in file names
- Maximum file name length: 255 bytes (UTF-8 encoded)
- The extension `.ldfx` is reserved exclusively for this format and must not be reused for any other purpose

**Valid examples:**
```
annual-report-2025.ldfx
user_manual_v2.ldfx
research-paper.ldfx
technical_spec_1_0.ldfx
```

**Invalid examples:**
```
Annual Report.ldfx        ← spaces not allowed
report.LDFX               ← uppercase extension not allowed
document.ldfx.zip         ← double extension not allowed
my.document.ldfx          ← dots in base name not allowed
```

---

## 4. UTF Encoding Policy

| Field | Value |
|---|---|
| All text content | UTF-8 |
| BOM (Byte Order Mark) | Prohibited in all text files |
| Null bytes in text fields | Prohibited |
| Line endings in text fields | LF (`\n`) only — CRLF is not permitted |
| Unicode Normalization | NFC (Canonical Decomposition followed by Canonical Composition) |
| Minimum Unicode version | Unicode 15.0 |

All JSON metadata, manifest files, and text-based content within an LDFX container must be encoded in UTF-8 without BOM.

Binary assets (images, audio, video, 3D objects) are exempt from the UTF-8 requirement but must be stored with correct binary encoding as defined in the Asset Specification (Module 10).

## 6. Architectural Decision — Container Format

### Decision: ZIP-based Container with Prepended LDFX Binary Header

**Chosen:** Option B — ZIP-based Container with a 64-byte prepended LDFX Binary Header.

---

### 6.1 Options Evaluated

#### Option A — Pure Binary Container

A fully custom binary format where all internal structure is defined by a proprietary binary layout.

**Advantages:**
- Maximum control over internal layout
- Potentially faster with a custom-built parser
- No dependency on the ZIP specification

**Disadvantages:**
- Requires implementing a complete container parser from scratch in every language and platform
- No existing tooling ecosystem — no inspection, repair, or extraction tools
- Higher attack surface due to custom parsing logic with no prior security audit history
- Harder to inspect, debug, and audit by third parties
- Incompatible with standard archive tools
- Significantly higher implementation and maintenance cost
- Streaming and random-access support must be custom-built
- Violates Open Standard Ready and Zero Vendor Lock-in principles

#### Option B — ZIP-based Container with Binary Header (CHOSEN)

A standard ZIP archive with a prepended fixed-size LDFX binary header that identifies the file before ZIP parsing begins.

**Advantages:**
- ZIP is a proven, battle-tested container format with 30+ years of production use
- Existing parsers available in every major language and platform
- Random access to individual entries without full decompression
- Streaming support via ZIP streaming mode
- Tooling ecosystem already exists (inspection, repair, extraction)
- Widely understood and audited by security researchers
- Supports per-entry compression (Deflate, Store; Zstandard in future versions)
- Supports large files via ZIP64 extension (files and archives beyond 4 GB)
- The binary header provides fast format identification before ZIP parsing begins
- Follows the established pattern used by EPUB, DOCX, JAR, APK, ODF
- Satisfies Open Standard Ready, Zero Vendor Lock-in, and Extensibility First principles

**Disadvantages:**
- ZIP specification constraints apply (fully mitigated by ZIP64)
- Slightly more complex header design (binary header + ZIP structure)
- ZIP does not natively support encryption at the container level (mitigated by LDFX Security Layer defined in Module 09)

#### Option C — 7Z Container

**Rejected** because:
- 7Z is not as universally supported as ZIP across all target platforms
- The 7Z specification is less stable and less widely implemented
- LZMA compression (7Z default) is slower to decompress than Deflate for random access
- Does not follow the established pattern of document format containers

---

### 6.2 Final Container Architecture

```
┌─────────────────────────────────────────────────────────┐
│  LDFX Binary Header  (64 bytes, offset 0–63)            │
├─────────────────────────────────────────────────────────┤
│  ZIP Archive Body    (offset 64 onward)                  │
│                                                         │
│  ├── manifest.json          (required)                  │
│  ├── metadata/              (required)                  │
│  │   └── metadata.json                                  │
│  ├── pages/                 (required)                  │
│  ├── assets/                (optional)                  │
│  ├── scripts/               (optional)                  │
│  ├── annotations/           (optional)                  │
│  ├── security/              (required)                  │
│  ├── cache/                 (optional, runtime-managed) │
│  ├── thumbnails/            (optional)                  │
│  ├── plugins/               (optional)                  │
│  ├── ai/                    (optional)                  │
│  └── logs/                  (optional, runtime-managed) │
└─────────────────────────────────────────────────────────┘
```

The ZIP archive begins at byte offset 64. All LDFX-aware parsers must skip the first 64 bytes before invoking ZIP parsing logic.

Standard ZIP tools that do not understand the LDFX header will fail to open the file directly. This is intentional — it prevents accidental extraction of LDFX internals by non-LDFX tools while still allowing LDFX-aware tools to use standard ZIP libraries internally.

---

## 7. Engineering Notes

1. The `.ldfx` extension must never be reused for a different format version. Breaking format changes must introduce a new major version negotiated via the binary header version field (defined in Module 02).
2. MIME type registration with IANA must be pursued once the specification reaches v1.0 stable.
3. The ZIP-based container ensures LDFX files can be partially inspected by LDFX-aware tools using standard ZIP libraries, which aids debugging, security auditing, and disaster recovery.
4. The binary header ensures LDFX files are unambiguously identifiable by magic bytes before any ZIP parsing occurs, preventing format confusion attacks.
5. All text content within the container must pass UTF-8 validation before the document is considered valid.

---

## 8. Future Compatibility Considerations

- If ZIP is superseded by a superior container format, the binary header version field allows the container format to be changed in a future major version without changing the file extension or MIME type.
- The MIME type `application/vnd.ldfx` is version-agnostic. Version negotiation is handled internally via the binary header version field.
- All future format versions must remain identifiable by the same magic bytes at byte offset 0.
- The naming convention rules are intentionally strict to ensure cross-platform compatibility across case-sensitive (Linux) and case-insensitive (Windows, macOS) file systems.
