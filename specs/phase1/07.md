# Module 07 — LDFX Version Management System

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** Module 01, Module 02, Module 05, Module 06
**Required By:** Module 08, Module 09, Module 12, final_integration

---

## 1. Purpose

This module defines the complete version management system for the LDFX ecosystem. It governs four distinct versioning domains:

1. **Specification Version** — the LDFX format specification itself
2. **Document Version** — individual document revisions
3. **Runtime Version** — the LDFX runtime engine
4. **Plugin Version** — individual plugin packages

Each domain has independent versioning but they interact through a defined compatibility matrix.

---

## 2. Versioning Scheme Decision

### Decision: Strict Semantic Versioning (SemVer 2.0.0)

**Chosen:** Strict Semantic Versioning as defined at [semver.org](https://semver.org), format: `MAJOR.MINOR.PATCH`.

### 2.1 Options Evaluated

#### Option A — Strict Semantic Versioning (CHOSEN)

Format: `MAJOR.MINOR.PATCH` (e.g. `1.4.2`)

**Advantages:**
- Universally understood by engineers across all ecosystems
- Encodes compatibility intent directly in the version number
- MAJOR bump = breaking change (parsers must reject or warn)
- MINOR bump = backward-compatible addition (parsers must accept)
- PATCH bump = backward-compatible fix (parsers must accept)
- Enables automated compatibility checks
- Consistent with Rust/Cargo, npm, and most modern ecosystems
- Satisfies Backward Compatibility and Forward Compatibility principles

**Disadvantages:**
- Does not encode release date (mitigated by `created_at` / `modified_at` timestamps)

#### Option B — Calendar Versioning (CalVer)

Format: `YYYY.MM.DD` or `YYYY.MM` (e.g. `2025.07.01`)

**Rejected** because:
- Does not encode compatibility intent — a `2025.07` release may or may not be compatible with `2025.06`
- Cannot express patch releases without ambiguity
- Automated compatibility checks require additional metadata
- Does not align with the Rust/Cargo ecosystem used by this project
- Violates the Backward Compatibility and Forward Compatibility principles by making compatibility implicit rather than explicit

## 3. Specification Version

### 3.1 Definition

The Specification Version identifies the version of the LDFX format specification itself. It governs what fields, structures, and behaviors are valid in an LDFX document.

### 3.2 Storage Locations

| Location | Field | Module |
|---|---|---|
| Binary header | bytes 6–8 (Major, Minor, Patch) | Module 02 |
| `manifest.json` | `document.spec_version` | Module 05 |
| `metadata.json` | `document.spec_version` | Module 06 |
| `manifest.json` | `compatibility.min_spec_version` | Module 05 |

### 3.3 Versioning Rules

| Change Type | Version Bump | Examples |
|---|---|---|
| Breaking change to binary header | MAJOR | Changing magic bytes, header layout |
| Breaking change to manifest schema | MAJOR | Removing required fields, changing field types |
| Breaking change to container structure | MAJOR | Renaming required folders |
| New optional field in manifest | MINOR | Adding `document.subtitle` |
| New optional folder | MINOR | Adding `thumbnails/` |
| New feature flag | MINOR | Adding `HAS_FORMS` bit |
| Bug fix in specification text | PATCH | Clarifying ambiguous wording |
| Typo correction | PATCH | No behavioral change |

### 3.4 Current Version

`1.0.0`

## 4. Document Version

### 4.1 Definition

The Document Version identifies a specific revision of a document's content. It is independent of the Specification Version.

### 4.2 Storage Location

| Location | Field | Module |
|---|---|---|
| `metadata.json` | `version.document_version` | Module 06 |
| `metadata.json` | `version.revision` | Module 06 |

### 4.3 Versioning Rules

| Change Type | Version Bump |
|---|---|
| Structural reorganization, major content rewrite | MAJOR |
| Significant content addition, new sections | MINOR |
| Typo fixes, minor corrections, formatting | PATCH |

### 4.4 Revision Counter

The `revision` field is a monotonically increasing integer starting at 1. It increments on every save, regardless of the semantic version bump. It provides a total ordering of all document saves.

**Rule:** `revision` must never decrease. If a document is restored from a backup, the revision counter must continue from the highest known revision.

## 5. Runtime Version

### 5.1 Definition

The Runtime Version identifies the version of the LDFX runtime engine. It determines which specification versions the runtime can parse and execute.

### 5.2 Compatibility Rules

A runtime version `R` can open a document with specification version `S` if:

```
R.MAJOR == S.MAJOR
AND
R.MINOR >= S.MINOR
```

| Runtime | Document Spec | Result |
|---|---|---|
| 1.0.0 | 1.0.0 | ✅ Compatible |
| 1.2.0 | 1.0.0 | ✅ Compatible (runtime is newer) |
| 1.0.0 | 1.2.0 | ⚠️ Partial (runtime is older — unknown fields ignored) |
| 2.0.0 | 1.0.0 | ❌ Incompatible (major version mismatch) |
| 1.0.0 | 2.0.0 | ❌ Incompatible (major version mismatch) |

### 5.3 Unknown Field Policy

When a runtime encounters a field or feature it does not recognize:

- If `manifest.json` `compatibility.unknown_feature_policy` is `warn` → log a warning and continue
- If `manifest.json` `compatibility.unknown_feature_policy` is `error` → reject the document
- If `manifest.json` `compatibility.unknown_feature_policy` is `ignore` → silently skip

Default policy: `warn`.

## 6. Plugin Version

### 6.1 Definition

Plugin versions are independent of the specification version and runtime version. Each plugin declares its own version and its minimum compatible runtime version.

### 6.2 Storage Location

| Location | Field | Module |
|---|---|---|
| `manifest.json` `plugins[]` | `version` | Module 05 |
| `manifest.json` `plugins[]` | `minimum_version` | Module 05 |
| `plugins/index.json` | per-plugin version | Module 12 |

### 6.3 Compatibility Rules

A plugin version `P` is compatible with runtime version `R` if:

```
P.minimum_runtime_version.MAJOR == R.MAJOR
AND
R.MINOR >= P.minimum_runtime_version.MINOR
```

## 7. Breaking Changes Policy

### 7.1 Definition of Breaking Change

A breaking change is any modification that causes a previously valid LDFX document to:
- Fail to open in a compliant runtime
- Render incorrectly in a compliant runtime
- Lose data when round-tripped through a compliant runtime

### 7.2 Breaking Change Process

1. Breaking change is proposed with full justification
2. A deprecation period of at least one MINOR version must precede any MAJOR bump
3. The deprecated behavior is documented in the specification changelog
4. The MAJOR version is incremented
5. Migration guidance is published

### 7.3 Deprecation

Deprecated features:
- Are listed in `manifest.json` `compatibility.deprecated_features`
- Continue to function for at least one full MAJOR version after deprecation
- Are removed only in the next MAJOR version after the deprecation MAJOR version

## 8. Compatibility Matrix

### 8.1 Specification vs Runtime

| Spec Version | Min Runtime | Max Runtime | Notes |
|---|---|---|---|
| 1.0.x | 1.0.0 | 1.x.x | Any 1.x runtime |
| 1.1.x | 1.1.0 | 1.x.x | Requires runtime ≥ 1.1.0 |
| 1.2.x | 1.2.0 | 1.x.x | Requires runtime ≥ 1.2.0 |
| 2.0.x | 2.0.0 | 2.x.x | New major — separate runtime |

### 8.2 Document Version vs Specification Version

Document versions are independent. A document at version `5.2.1` may be authored against specification `1.0.0`. The specification version governs format validity; the document version governs content revision.

### 8.3 Plugin vs Runtime

| Plugin Min Runtime | Runtime 1.0 | Runtime 1.1 | Runtime 1.2 | Runtime 2.0 |
|---|---|---|---|---|
| 1.0.0 | ✅ | ✅ | ✅ | ❌ |
| 1.1.0 | ❌ | ✅ | ✅ | ❌ |
| 1.2.0 | ❌ | ❌ | ✅ | ❌ |
| 2.0.0 | ❌ | ❌ | ❌ | ✅ |

## 9. Version Field Validation Rules

| Rule | Severity | Condition |
|---|---|---|
| `spec_version` not valid SemVer | Fatal | Does not match `MAJOR.MINOR.PATCH` pattern |
| Binary header version ≠ manifest spec_version | Fatal | Mismatch between header bytes 6–8 and manifest field |
| Manifest spec_version ≠ metadata spec_version | Fatal | Cross-file version mismatch |
| Runtime MAJOR ≠ document spec MAJOR | Fatal | Major version incompatibility |
| Runtime MINOR < document spec MINOR | Warning | Runtime may not support all features |
| `version.revision` < 1 | Fatal | Revision must start at 1 |
| `version.revision` decreased | Fatal | Revision must be monotonically increasing |
| Deprecated feature used | Warning | Feature listed in `deprecated_features` |
| Plugin version incompatible with runtime | Fatal | If plugin is `required: true` |
| Plugin version incompatible with runtime | Warning | If plugin is `required: false` |

## 10. Future Evolution

- When LDFX 2.0.0 is released, a separate binary header major version byte will distinguish 1.x from 2.x documents.
- The `_reserved` fields in `manifest.json` and `metadata.json` provide extension points for new version-related fields without breaking existing parsers.
- Long-term version archive: every published specification version is permanently archived at `https://spec.ldfx.org/versions/<MAJOR>.<MINOR>.<PATCH>/`.
