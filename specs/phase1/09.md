# Module 09 — LDFX Security Policy Specification

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** Module 01, Module 02, Module 03, Module 04, Module 05, Module 06, Module 07, Module 08
**Required By:** Module 10, Module 11, Module 12, final_integration

---

## 1. Purpose

This module defines the complete security architecture for the LDFX ecosystem. Security is not a feature — it is a foundational property of every layer of the format, runtime, and tooling.

The threat model assumes that any LDFX document received from an external source is potentially hostile until proven otherwise.

---

## 2. Runtime Security Model Decision

### Decision: Permission-Based Runtime with Mandatory Sandbox

**Chosen:** A permission-based runtime where all execution occurs inside a mandatory sandbox, and capabilities beyond the baseline require explicit user-granted permissions.

### 2.1 Options Evaluated

#### Option A — Sandbox-Only Runtime

All scripts and plugins execute in a fully isolated sandbox with no capability to interact with the host system under any circumstances.

**Advantages:**
- Maximum security — no attack surface beyond the sandbox boundary
- Simple security model — no permission negotiation

**Disadvantages:**
- Severely limits document capabilities — no network access, no file access, no AI execution
- Cannot support the full LDFX feature set (AI engine, cloud sync, plugin SDK)
- Violates the AI Native and Plugin Friendly principles
- Documents cannot implement legitimate interactive features that require host access

#### Option B — Permission-Based Runtime with Mandatory Sandbox (CHOSEN)

All execution occurs inside a mandatory sandbox. Scripts and plugins may request additional capabilities via a declared permission system. Users explicitly grant or deny permissions. No capability is granted implicitly.

**Advantages:**
- Sandbox is always active — no code executes outside the sandbox without explicit permission
- Supports the full LDFX feature set through the permission system
- Users have full visibility and control over what a document can do
- Consistent with the security model of modern browsers, Android, and iOS
- Satisfies Security by Design, Plugin Friendly, and AI Native principles
- Permissions are declared in `manifest.json` — auditable before opening

**Disadvantages:**
- More complex implementation than sandbox-only
- Requires a well-designed permission UI to avoid permission fatigue

## 3. Sandbox Architecture

### 3.1 Sandbox Boundaries

Every script and plugin executes inside a WebAssembly (WASM) sandbox. The WASM sandbox provides:

- Memory isolation — each script/plugin has its own linear memory
- No direct system calls — all host interactions go through the LDFX Runtime API
- Deterministic execution — no undefined behavior
- Resource limits — CPU time, memory, and I/O are bounded

### 3.2 Sandbox Capabilities (Always Available)

These capabilities are available to all scripts and plugins without permission:

| Capability | Description |
|---|---|
| Read own page content | Read the pages the script is embedded in |
| Read own asset references | Read assets declared in the document |
| Render output | Write to the document's render surface |
| Read document metadata | Read `manifest.json` and `metadata.json` |
| Emit events | Send events to the LDFX event system |
| Log messages | Write to the runtime log |

### 3.3 Permission-Gated Capabilities

These capabilities require explicit user permission:

| Permission Name | Capability | Risk Level |
|---|---|---|
| `read_all_pages` | Read all pages in the document | Low |
| `write_annotations` | Create and modify annotations | Low |
| `read_annotations` | Read all annotations | Low |
| `network_read` | Make outbound HTTP GET requests | Medium |
| `network_write` | Make outbound HTTP POST/PUT requests | High |
| `filesystem_read` | Read files from the host filesystem | High |
| `filesystem_write` | Write files to the host filesystem | Critical |
| `execute_ai` | Run AI inference | Medium |
| `clipboard_read` | Read from system clipboard | Medium |
| `clipboard_write` | Write to system clipboard | Low |
| `notifications` | Display system notifications | Low |
| `camera` | Access device camera | Critical |
| `microphone` | Access device microphone | Critical |
| `geolocation` | Access device location | High |

### 3.4 Permission Declaration

Permissions must be declared in `manifest.json` `plugins[].permissions` and `scripts/index.json` before they can be requested at runtime. Undeclared permissions are automatically denied.

## 4. Digital Signatures

### 4.1 Purpose

Digital signatures provide:
- **Authenticity** — proof that the document was created by a specific entity
- **Integrity** — proof that the document has not been modified since signing
- **Non-repudiation** — the signer cannot deny having signed the document

### 4.2 Supported Signature Algorithms

| Algorithm | Status | Key Size | Notes |
|---|---|---|---|
| `ed25519` | Preferred | 256-bit | Fast, small signatures, modern |
| `ecdsa-p256-sha256` | Supported | 256-bit | Widely supported |
| `rsa-pss-sha256` | Supported | 2048-bit minimum | Legacy compatibility |
| `dilithium3` | Future | Post-quantum | Reserved for quantum-safe phase |

### 4.3 Signature Coverage

A document signature must cover:
- All entries in `pages/`
- All entries in `assets/`
- All entries in `scripts/`
- All entries in `plugins/`
- All entries in `ai/`
- `manifest.json`
- `metadata/metadata.json`

The signature must NOT cover:
- `cache/` — runtime-generated, changes frequently
- `logs/` — runtime-generated, changes frequently
- `thumbnails/` — regenerated locally
- `annotations/` — user-generated after signing

### 4.4 Signature Storage

Signatures are stored in `security/signatures.json`:

```json
{
  "schema_version": "1.0.0",
  "signatures": [
    {
      "id": "sig-uuid-v4",
      "algorithm": "ed25519",
      "signer_id": "publisher-uuid-v4",
      "signer_name": "<publisher name>",
      "certificate_path": "security/certificates/publisher.pem",
      "signed_at": "2025-07-01T00:00:00Z",
      "coverage": "full",
      "signature_value": "<base64-encoded-signature>",
      "hashes_ref": "security/hashes.json"
    }
  ]
}
```

### 4.5 Trust Levels

| Level | Description | Requirements |
|---|---|---|
| `untrusted` | No signature | Document opened with maximum restrictions |
| `self-signed` | Signed with self-generated key | User must explicitly trust |
| `trusted` | Signed with a key in the user's trust store | Elevated permissions available |
| `verified-publisher` | Signed with a key in the LDFX publisher registry | Full permissions available |

## 5. Hashing and Integrity

### 5.1 Hash Algorithm

| Algorithm | Status | Notes |
|---|---|---|
| `sha256` | Required | Minimum for all documents |
| `sha3-256` | Optional | Additional integrity layer |
| `blake3` | Future | Reserved for performance-critical use |

### 5.2 Hashes File

`security/hashes.json` contains SHA-256 hashes of every content entry:

```json
{
  "schema_version": "1.0.0",
  "algorithm": "sha256",
  "computed_at": "2025-07-01T00:00:00Z",
  "entries": {
    "manifest.json": "sha256:<hex>",
    "metadata/metadata.json": "sha256:<hex>",
    "pages/index.json": "sha256:<hex>",
    "pages/page_001/content.json": "sha256:<hex>",
    "assets/images/a3f9c2d1.webp": "sha256:<hex>"
  }
}
```

### 5.3 Hash Verification Rules

- Hashes are verified in Stage 7 of validation (Module 08)
- A hash mismatch is a fatal validation error
- `cache/` and `logs/` entries are excluded from hashes
- `security/hashes.json` itself is not hashed (it is covered by the digital signature)

## 6. Encryption

### 6.1 Encryption Architecture

LDFX uses application-level encryption, not ZIP-level encryption (ZIP native encryption is prohibited per Module 03 §3).

Encryption is applied to individual entries or the entire document body before they are stored in the ZIP container.

### 6.2 Supported Encryption Algorithms

| Algorithm | Status | Notes |
|---|---|---|
| `AES-256-GCM` | Required | Authenticated encryption, preferred |
| `ChaCha20-Poly1305` | Supported | Alternative for constrained environments |
| `CRYSTALS-Kyber` | Future | Post-quantum key encapsulation |

### 6.3 Encryption Scope

| Scope | Description |
|---|---|
| `full` | Entire document body encrypted (all entries except `manifest.json`) |
| `content` | Only `pages/` and `assets/` encrypted |
| `selective` | Individual entries encrypted as declared in `manifest.json` |

`manifest.json` is never encrypted — it must be readable to determine encryption parameters.

### 6.4 Key Management

- Encryption keys are never stored inside the LDFX file
- Key derivation uses PBKDF2-SHA256 (minimum 600,000 iterations) for password-based encryption
- Key exchange for multi-recipient documents uses X25519 ECDH
- Key metadata (algorithm, salt, IV) is stored in `security/encryption.json`

---

## 7. Certificate Support

### 7.1 Certificate Format

X.509 v3 certificates in PEM format, stored in `security/certificates/`.

### 7.2 Certificate Validation

| Check | Requirement |
|---|---|
| Certificate chain | Must chain to a trusted root |
| Certificate expiry | Must not be expired at time of signing |
| Key usage | Must include `digitalSignature` |
| Extended key usage | Must include `documentSigning` or `codeSigning` |
| Revocation | CRL or OCSP check when network is available |

### 7.3 Trusted Publisher Registry

The LDFX Trusted Publisher Registry is a curated list of verified publisher certificates. Documents signed by registered publishers receive `verified-publisher` trust level.

The registry is distributed as a signed JSON file bundled with the runtime and updated periodically.

---

## 8. Plugin Trust

### 8.1 Plugin Trust Levels

| Level | Requirements | Capabilities |
|---|---|---|
| `untrusted` | No signature | Sandbox only, no permission-gated capabilities |
| `signed` | Valid signature, not in registry | Sandbox + declared low-risk permissions |
| `verified` | Signature from verified publisher | Sandbox + all declared permissions |

### 8.2 Plugin Isolation

Each plugin runs in its own isolated WASM sandbox. Plugins cannot:
- Access other plugins' memory
- Access the host filesystem without `filesystem_read`/`filesystem_write` permission
- Communicate with other plugins except through the LDFX event system
- Escalate their own permissions at runtime

---

## 9. Script Permissions

Scripts declare their required permissions in `scripts/index.json`. The runtime presents a permission request dialog to the user before executing any script that requires permissions beyond the baseline.

Scripts that attempt to use undeclared permissions receive a runtime error, not a silent failure.

---

## 10. Network Permissions

| Permission | Scope | User Prompt |
|---|---|---|
| `network_read` | HTTP GET to declared domains only | Yes |
| `network_write` | HTTP POST/PUT to declared domains only | Yes |

Declared domains are listed in `scripts/index.json` or `plugins/index.json`. Requests to undeclared domains are blocked without user prompt.

---

## 11. Filesystem Permissions

| Permission | Scope | User Prompt |
|---|---|---|
| `filesystem_read` | User-selected files via OS file picker only | Yes — OS picker shown |
| `filesystem_write` | User-selected locations via OS save dialog only | Yes — OS dialog shown |

Direct filesystem path access is never permitted. All filesystem access goes through OS-mediated dialogs.

---

## 12. Macro Execution

Macros are treated as scripts. All macro execution rules from §3 apply. There is no separate macro execution model — macros are scripts with a simplified authoring interface.

---

## 13. AI Execution

AI inference is a permission-gated capability (`execute_ai`). The AI engine runs inside the LDFX sandbox. AI models embedded in `ai/` are executed by the LDFX AI Engine, not by the host OS.

AI execution constraints:
- Maximum inference time: configurable, default 30 seconds
- Maximum memory: configurable, default 4 GB
- No network access during inference unless `network_read` is also granted
- AI output is treated as untrusted content and sanitized before rendering

## 14. Threat Model

### 14.1 Assets Under Protection

| Asset | Threat |
|---|---|
| Document content | Unauthorized modification, tampering |
| User data | Exfiltration via malicious scripts |
| Host filesystem | Unauthorized read/write |
| Host network | Unauthorized outbound connections |
| Host credentials | Phishing via document UI |
| Runtime integrity | Malicious plugin compromising the runtime |

### 14.2 Threat Actors

| Actor | Capability |
|---|---|
| Malicious document author | Embeds hostile scripts, plugins, or AI models |
| Man-in-the-middle | Modifies document in transit |
| Malicious plugin publisher | Publishes plugin with hidden capabilities |
| Compromised publisher key | Signs malicious documents with trusted key |

### 14.3 Attack Surface

| Surface | Mitigation |
|---|---|
| Binary header parsing | Strict validation, CRC32 integrity check |
| ZIP parsing | Use audited ZIP library, path traversal prevention |
| JSON parsing | Use strict JSON parser, schema validation |
| Script execution | WASM sandbox, permission system |
| Plugin execution | WASM sandbox, plugin trust levels |
| Asset rendering | Sanitize all asset data before rendering |
| Network requests | Domain allowlist, user permission required |
| Filesystem access | OS-mediated dialogs only |

---

## 15. Recovery

### 15.1 Security Failure Recovery

| Failure | Recovery Action |
|---|---|
| Hash mismatch | Reject document, offer to open in read-only recovery mode |
| Invalid signature | Downgrade trust level, warn user, offer to open as untrusted |
| Expired certificate | Warn user, allow opening as `self-signed` trust level |
| Revoked certificate | Reject document if online, warn if offline |
| Sandbox escape attempt | Terminate script/plugin, log incident, notify user |
| Permission violation | Deny capability, log incident, notify user |

## 16. Future Quantum-Safe Cryptography

The LDFX security architecture is designed to support post-quantum cryptography as a future upgrade:

| Current Algorithm | Post-Quantum Replacement | Status |
|---|---|---|
| `ed25519` (signatures) | `dilithium3` (CRYSTALS-Dilithium) | Reserved |
| `X25519` (key exchange) | `CRYSTALS-Kyber` | Reserved |
| `AES-256-GCM` (encryption) | Remains secure (symmetric) | No change needed |

Migration path:
1. A future MINOR version will add `dilithium3` as a supported signature algorithm
2. Documents may carry both `ed25519` and `dilithium3` signatures simultaneously during the transition period
3. A future MAJOR version will require `dilithium3` as the minimum signature algorithm
