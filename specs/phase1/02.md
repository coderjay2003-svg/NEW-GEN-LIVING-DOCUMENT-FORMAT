# Module 02 — LDFX Binary Header Specification

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** Module 01 (Format Identity)
**Required By:** Module 03, Module 08, Module 09

---

## 1. Purpose

The LDFX Binary Header is a fixed-size block prepended to every LDFX file at byte offset 0.

Its responsibilities are:

- Unambiguous format identification via magic bytes
- Format version declaration
- Feature flag signaling
- Integrity verification of the header itself
- Container format identification
- Reserved space for future expansion

The header must be parseable without loading the ZIP container body. It is the first thing any LDFX parser reads.

---

## 2. Header Size Decision

### Decision: Option C — 64-byte Header

**Chosen:** 64 bytes.

### 2.1 Options Evaluated

#### Option A — 16-byte Header

**Rejected** because:
- Insufficient space for magic bytes, version, flags, integrity, and reserved fields simultaneously
- No room for future expansion without breaking the format
- Forces critical fields to be packed too tightly, reducing readability and extensibility
- Cannot accommodate a full SHA-256 integrity field (32 bytes alone)

#### Option B — 32-byte Header

**Rejected** because:
- Still insufficient once magic bytes (8), version (4), flags (4), and a minimal integrity field are included
- A 32-byte SHA-256 integrity field alone would consume the entire header
- No reserved space for future fields
- Would require a breaking change to expand

#### Option C — 64-byte Header (CHOSEN)

**Chosen** because:
- Provides space for all required fields with room for future expansion
- Allows a full 8-byte magic sequence
- Accommodates version, flags, container type, and integrity fields without compression
- 32 bytes of reserved space ensures the header never needs to grow in a breaking way
- 64 bytes is a natural CPU cache-line-aligned size on modern architectures
- Consistent with the approach taken by other mature binary formats (ELF: 64 bytes, PNG: 8-byte magic + structured header)

## 3. Complete Byte Layout

```
Offset  Size   Field                  Type        Description
──────  ─────  ─────────────────────  ──────────  ──────────────────────────────────────────
0       4      Magic Bytes            u8[4]       Fixed: 0x4C 0x44 0x46 0x58 ("LDFX")
4       2      Format Signature       u8[2]       Fixed: 0x1A 0x0A (format guard bytes)
6       1      Major Version          u8          Specification major version (e.g. 1)
7       1      Minor Version          u8          Specification minor version (e.g. 0)
8       1      Patch Version          u8          Specification patch version (e.g. 0)
9       1      Container Type         u8          0x01 = ZIP, reserved for future containers
10      2      Feature Flags          u16 LE      Bitmask of enabled features (see §4)
12      2      Header Flags           u16 LE      Bitmask of header-level properties (see §5)
14      2      Reserved A             u8[2]       Must be 0x00 0x00 — reserved for future use
16      4      Document Epoch         u32 LE      Unix timestamp (seconds) of document creation
20      4      Header CRC32           u32 LE      CRC32 of bytes 0–19 (header self-integrity)
24      8      Reserved B             u8[8]       Must be all 0x00 — reserved for future use
32      16     Instance UUID Prefix   u8[16]      First 16 bytes of the document UUID (see §6)
48      16     Reserved C             u8[16]      Must be all 0x00 — reserved for future use
──────  ─────  ─────────────────────  ──────────  ──────────────────────────────────────────
Total   64 bytes
```

## 4. Feature Flags (bytes 10–11, u16 Little Endian)

Each bit represents a feature that is active in this document.

| Bit | Mask   | Name                  | Description |
|-----|--------|-----------------------|-------------|
| 0   | 0x0001 | `HAS_SCRIPTS`         | Document contains executable scripts |
| 1   | 0x0002 | `HAS_AI`              | Document contains AI engine data |
| 2   | 0x0004 | `HAS_PLUGINS`         | Document declares plugin dependencies |
| 3   | 0x0008 | `HAS_ENCRYPTION`      | Document body is encrypted |
| 4   | 0x0010 | `HAS_DIGITAL_SIG`     | Document carries a digital signature |
| 5   | 0x0020 | `HAS_ANNOTATIONS`     | Document contains annotations |
| 6   | 0x0040 | `HAS_COLLABORATION`   | Document supports collaborative editing |
| 7   | 0x0080 | `HAS_CLOUD_SYNC`      | Document is linked to cloud synchronization |
| 8   | 0x0100 | `HAS_3D`              | Document contains 3D assets |
| 9   | 0x0200 | `HAS_VIDEO`           | Document contains video assets |
| 10  | 0x0400 | `HAS_AUDIO`           | Document contains audio assets |
| 11  | 0x0800 | `HAS_FORMS`           | Document contains interactive forms |
| 12  | 0x1000 | `HAS_VERSION_HISTORY` | Document carries embedded version history |
| 13  | 0x2000 | `READONLY`            | Document is marked read-only |
| 14  | 0x4000 | Reserved              | Must be 0 |
| 15  | 0x8000 | Reserved              | Must be 0 |

A parser encountering an unknown set bit in a reserved position must treat it as a warning, not a fatal error, to support forward compatibility.

---

## 5. Header Flags (bytes 12–13, u16 Little Endian)

Header flags describe properties of the header and container itself.

| Bit | Mask   | Name                  | Description |
|-----|--------|-----------------------|-------------|
| 0   | 0x0001 | `ZIP64`               | Container uses ZIP64 extensions |
| 1   | 0x0002 | `COMPRESSED_MANIFEST` | manifest.json is stored compressed |
| 2   | 0x0004 | `SIGNED_HEADER`       | Header itself carries a detached signature in security/ |
| 3   | 0x0008 | `DRAFT`               | Document is a draft — not finalized |
| 4   | 0x0010 | `TEMPLATE`            | Document is a template |
| 5   | 0x0020 | Reserved              | Must be 0 |
| 6–15 | —     | Reserved              | Must be 0 |

---

## 6. Instance UUID Prefix (bytes 32–47)

The 16-byte field at offset 32 stores the first 16 bytes of the document's UUID v4.

The full UUID (32 hex characters) is stored in `manifest.json`. The prefix in the header allows fast document identity checks without opening the ZIP container.

UUID format: RFC 4122 UUID v4 (random), stored as raw 16 bytes (not as a string).

---

## 7. Magic Bytes

| Bytes | Hex | ASCII |
|---|---|---|
| 0–3 | `4C 44 46 58` | `LDFX` |
| 4–5 | `1A 0A` | Format guard (non-printable, prevents text editor corruption) |

The guard bytes `0x1A 0x0A` serve two purposes:
- `0x1A` (Ctrl+Z / EOF on DOS) causes DOS/Windows `type` command to stop, preventing accidental display
- `0x0A` (LF) detects line-ending corruption — if a tool converts LF to CRLF, the header becomes invalid

This pattern is directly inspired by the PNG format's magic byte design, which has proven highly effective.

---

## 8. Endianness

All multi-byte integer fields in the LDFX binary header use **Little Endian** byte order.

Rationale: The primary target platforms (x86-64, ARM64) are natively little-endian. Using little-endian avoids byte-swap overhead on the most common hardware.

---

## 9. Parsing Rules

1. Read exactly 64 bytes from offset 0.
2. Verify bytes 0–3 equal `4C 44 46 58`. If not, reject — not an LDFX file.
3. Verify bytes 4–5 equal `1A 0A`. If not, reject — file may be corrupted (line-ending conversion).
4. Read Major Version (byte 6), Minor Version (byte 7), Patch Version (byte 8).
5. Verify the runtime supports this specification version (see Module 07 compatibility rules).
6. Read Container Type (byte 9). Currently only `0x01` (ZIP) is valid.
7. Read Feature Flags (bytes 10–11) as u16 LE.
8. Read Header Flags (bytes 12–13) as u16 LE.
9. Verify Reserved A (bytes 14–15) are both `0x00`. If not, emit a warning.
10. Read Document Epoch (bytes 16–19) as u32 LE.
11. Compute CRC32 of bytes 0–19. Compare with stored CRC32 at bytes 20–23. If mismatch, reject — header is corrupted.
12. Verify Reserved B (bytes 24–31) are all `0x00`. If not, emit a warning.
13. Read Instance UUID Prefix (bytes 32–47).
14. Verify Reserved C (bytes 48–63) are all `0x00`. If not, emit a warning.
15. Proceed to ZIP parsing starting at byte offset 64.

---

## 10. Validation Rules

| Rule | Severity | Condition |
|---|---|---|
| Magic bytes mismatch | Fatal | Bytes 0–3 ≠ `4C 44 46 58` |
| Guard bytes mismatch | Fatal | Bytes 4–5 ≠ `1A 0A` |
| Unsupported container type | Fatal | Byte 9 ≠ `0x01` (and not a known future value) |
| Header CRC32 mismatch | Fatal | Computed CRC32 of bytes 0–19 ≠ stored value at bytes 20–23 |
| Unsupported major version | Fatal | Major version > runtime maximum supported major version |
| Reserved A non-zero | Warning | Bytes 14–15 not all `0x00` |
| Reserved B non-zero | Warning | Bytes 24–31 not all `0x00` |
| Reserved C non-zero | Warning | Bytes 48–63 not all `0x00` |
| Unknown feature flag set | Warning | Bits 14–15 of Feature Flags are set |
| Unknown header flag set | Warning | Bits 5–15 of Header Flags are set |
| Future minor version | Info | Minor version > runtime maximum supported minor version |

---

## 11. Future Expansion Strategy

- Reserved fields A, B, and C (total 26 bytes) are available for future use without changing the header size.
- If a future version requires more than 26 bytes of new header fields, the Container Type field (byte 9) can be used to signal a new header format version.
- The CRC32 at bytes 20–23 covers only bytes 0–19 to allow bytes 20–63 to be extended in future versions without invalidating the core integrity check.
- Feature Flags bits 14–15 and Header Flags bits 5–15 are reserved for future features.

---

## 12. Consistency with Module 01

- The 64-byte header is prepended to the ZIP container as decided in Module 01.
- ZIP parsing begins at byte offset 64 as specified in Module 01.
- The magic bytes `LDFX` match the official short name defined in Module 01.
- The Container Type field supports the future replacement of ZIP with another container format as noted in Module 01 §8.
