# Module 03 — LDFX Container Architecture Specification

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** Module 01 (Format Identity), Module 02 (Binary Header)
**Required By:** Module 04, Module 05, Module 06, Module 08, Module 09

---

## 1. Purpose

This module defines the internal container architecture of an LDFX file. It specifies the container format choice, folder hierarchy, compression strategy, streaming support, random access support, and large file support.

---

## 2. Container Format Decision

### Decision: Option A — ZIP (with ZIP64 extension)

**Chosen:** Standard ZIP container with ZIP64 extension support, accessed at byte offset 64 (after the LDFX binary header defined in Module 02).

---

### 2.1 Options Evaluated

#### Option A — ZIP with ZIP64 (CHOSEN)

**Advantages:**
- Industry-proven format with 30+ years of production use
- ZIP64 removes all practical size limits (files and archives beyond 4 GB)
- Per-entry compression — each file inside the archive can use a different compression method
- Random access to any entry without decompressing the entire archive
- Streaming write support via ZIP streaming mode
- Parsers available in every major language and platform
- Existing tooling ecosystem for inspection, repair, and extraction
- Widely audited by security researchers
- Follows the established pattern of EPUB, DOCX, JAR, APK, ODF
- Satisfies Open Standard Ready, Zero Vendor Lock-in, Extensibility First

**Disadvantages:**
- ZIP specification constraints (fully mitigated by ZIP64)
- No native container-level encryption (mitigated by LDFX Security Layer, Module 09)

#### Option B — 7Z

**Rejected** because:
- Less universally supported across all target platforms
- LZMA compression is slower to decompress for random access patterns
- Specification is less stable and less widely implemented
- Fewer language bindings available
- Does not follow the established document container pattern

#### Option C — Custom Binary Container

**Rejected** because:
- Requires implementing a complete container parser from scratch
- No existing tooling or security audit history
- Violates Open Standard Ready and Zero Vendor Lock-in principles
- Higher attack surface, higher maintenance cost
- No streaming or random-access support without custom implementation

## 3. ZIP Configuration Rules

| Property | Value |
|---|---|
| ZIP version | 2.0 minimum, ZIP64 when required |
| ZIP64 trigger | Any entry ≥ 4 GB, or total archive ≥ 4 GB, or entry count > 65,535 |
| Compression methods allowed | Store (0), Deflate (8), Zstandard (93) — future |
| Encryption at ZIP level | Prohibited — encryption handled by LDFX Security Layer (Module 09) |
| ZIP comment field | Must be empty or contain only `LDFX/<major>.<minor>.<patch>` |
| Central directory | Must be present and valid |
| Data descriptors | Allowed for streaming-written entries |
| Entry name encoding | UTF-8 only (ZIP general purpose bit 11 must be set) |

## 6. System Folders

System folders are managed exclusively by the LDFX runtime. Authors and editors must not write to them directly.

| Folder | Managed By | Purpose |
|---|---|---|
| `cache/` | Runtime | Temporary render and decode cache |
| `logs/` | Runtime | Session and error logs |

System folder contents are not included in document integrity hashes (Module 08) and are not synchronized to cloud (Module 09 / Sync Engine).

---

## 7. Future Folders

The following folder names are reserved for future phases and must not be used by authors or plugins:

| Reserved Name | Intended Future Use |
|---|---|
| `collab/` | Real-time collaboration state |
| `history/` | Full version history snapshots |
| `index/` | Full-text search index |
| `extensions/` | Future extension mechanism |
| `runtime/` | Runtime state persistence |

Any LDFX parser encountering an unknown folder must ignore it and emit an informational log entry. Unknown folders must never cause a fatal error (forward compatibility rule).

## 8. Compression Strategy

### 8.1 Per-Entry Compression Policy

| Entry Type | Compression Method | Rationale |
|---|---|---|
| `manifest.json` | Store (no compression) | Must be readable instantly without decompression |
| `metadata/metadata.json` | Deflate | Text compresses well; not on critical path |
| `pages/*/content.json` | Deflate | Text content, high compression ratio |
| `pages/*/layout.json` | Deflate | Text content |
| `assets/images/*` | Store | Already compressed (JPEG, WebP, PNG) |
| `assets/audio/*` | Store | Already compressed (MP3, AAC, OPUS) |
| `assets/video/*` | Store | Already compressed (H.264, H.265, AV1) |
| `assets/fonts/*` | Deflate | Binary but compressible |
| `assets/vector/*` | Deflate | SVG/text compresses well |
| `assets/3d/*` | Deflate or Store | Depends on format |
| `scripts/*` | Deflate | Text/WASM compresses well |
| `annotations/*` | Deflate | JSON text |
| `security/*` | Store | Cryptographic data must not be recompressed |
| `thumbnails/*` | Store | Already compressed images |
| `plugins/*` | Deflate | Mixed content |
| `ai/*` | Deflate or Store | Depends on model format |
| `logs/*` | Deflate | Text compresses well |

### 8.2 Compression Level

Default Deflate compression level: 6 (balanced speed vs. ratio).

Editors may allow users to choose between:
- `fast` — Deflate level 1
- `balanced` — Deflate level 6 (default)
- `maximum` — Deflate level 9

## 9. Random Access Support

ZIP's central directory enables random access to any entry by name without reading the entire archive.

LDFX parsers must:
1. Read the ZIP central directory first.
2. Build an in-memory entry index keyed by entry path.
3. Access individual entries by seeking directly to their local file header offset.

This enables:
- Loading `manifest.json` without reading pages or assets
- Loading a single page without loading all pages
- Loading a single asset on demand (lazy loading)
- Incremental document loading for large documents

---

## 10. Streaming Support

LDFX supports streaming write mode for document creation in memory-constrained environments.

In streaming mode:
- Entries are written sequentially without seeking back to update local headers
- Data descriptors (ZIP signature `0x08074b50`) are used after each entry
- The central directory is written at the end of the stream
- The LDFX binary header (64 bytes) is written first

Streaming mode is write-only. Reading always requires random access to the central directory.

---

## 11. Large File Support

ZIP64 extensions are automatically activated when:
- Any single entry is ≥ 4,294,967,295 bytes (4 GB − 1)
- The total archive size is ≥ 4,294,967,295 bytes
- The number of entries exceeds 65,535

LDFX parsers must support ZIP64 on all platforms. ZIP64 support is not optional.

---

## 12. Validation Rules

| Rule | Severity | Condition |
|---|---|---|
| ZIP signature missing | Fatal | No valid ZIP end-of-central-directory record at offset 64+ |
| `manifest.json` missing | Fatal | No entry named `manifest.json` in ZIP root |
| `metadata/` missing | Fatal | No `metadata/` directory in ZIP |
| `pages/` missing | Fatal | No `pages/` directory in ZIP |
| `security/` missing | Fatal | No `security/` directory in ZIP |
| Entry name not UTF-8 | Fatal | ZIP general purpose bit 11 not set on any entry |
| ZIP-level encryption present | Fatal | Any entry uses ZIP native encryption |
| Unknown folder present | Info | Folder name not in known or reserved list |
| System folder modified by author | Warning | `cache/` or `logs/` present in author-created document |
| ZIP64 required but not used | Fatal | Entry or archive exceeds 4 GB without ZIP64 |
| Compressed manifest | Warning | `manifest.json` uses compression (should be stored) |

## 13. Consistency with Previous Modules

- ZIP archive begins at byte offset 64, consistent with Module 01 §6.3 and Module 02 §9 step 15.
- Container Type byte in the binary header is `0x01` (ZIP), consistent with Module 02 §3.
- Feature Flags in the binary header (Module 02 §4) map directly to the presence of optional folders: `HAS_SCRIPTS` → `scripts/`, `HAS_AI` → `ai/`, `HAS_PLUGINS` → `plugins/`, etc.
- All text entries use UTF-8 without BOM, consistent with Module 01 §4.
