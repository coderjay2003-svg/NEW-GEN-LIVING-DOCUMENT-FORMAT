# Module 10 — LDFX Asset Management System Specification

**Specification Version:** 1.0.0
**Status:** Canonical — Approved
**Depends On:** Module 01, Module 03, Module 04, Module 05, Module 08, Module 09
**Required By:** Module 11, Module 12, final_integration

---

## 1. Purpose

This module defines the complete asset management system for LDFX documents. It covers asset identification, naming, storage, referencing, deduplication, integrity, supported formats, and lifecycle management.

Assets are all binary and media resources embedded in or referenced by an LDFX document — images, audio, video, fonts, vector graphics, 3D objects, and structured data.

---

## 2. Asset Identification and Naming

### 2.1 Content-Addressed Naming

All assets are named by their content hash. This provides:
- Automatic deduplication — identical assets are stored once
- Integrity verification — name encodes expected content
- Stable references — name never changes if content does not change

**Naming format:**
```
<sha256-first-32-hex-chars>.<extension>
```

Example: `a3f9c2d1e4b78f01a3f9c2d1e4b78f02.webp`

The first 32 hex characters of the SHA-256 hash of the raw asset bytes, followed by the correct file extension.

### 2.2 Asset ID

Each asset also has a logical UUID v4 identifier declared in the asset index. The UUID is stable across renames and format conversions. Pages reference assets by UUID, not by filename.

---

## 3. Asset Index

Every document with assets must have an asset index at `assets/index.json`.

```json
{
  "schema_version": "1.0.0",
  "assets": [
    {
      "id": "asset-uuid-v4",
      "type": "image",
      "subtype": "webp",
      "path": "assets/images/a3f9c2d1e4b78f01a3f9c2d1e4b78f02.webp",
      "original_name": "hero-image.webp",
      "size_bytes": 204800,
      "width": 1920,
      "height": 1080,
      "duration_ms": null,
      "checksum": "sha256:a3f9c2d1e4b78f01a3f9c2d1e4b78f02<full-64-hex>",
      "mime_type": "image/webp",
      "created_at": "2025-07-01T00:00:00Z",
      "alt_text": "Hero image showing the document cover",
      "license_ref": null,
      "tags": []
    }
  ]
}
```

### 3.1 Asset Index Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Yes | UUID v4 — stable asset identifier |
| `type` | string | Yes | Asset category: `image`, `audio`, `video`, `font`, `vector`, `3d`, `data` |
| `subtype` | string | Yes | Format identifier: `webp`, `mp4`, `woff2`, `svg`, `glb`, `json`, etc. |
| `path` | string | Yes | Path inside ZIP to the asset file |
| `original_name` | string | No | Original filename before content-addressed rename |
| `size_bytes` | integer | Yes | Uncompressed size in bytes |
| `width` | integer | No | Width in pixels (images, video) |
| `height` | integer | No | Height in pixels (images, video) |
| `duration_ms` | integer | No | Duration in milliseconds (audio, video) |
| `checksum` | string | Yes | Full SHA-256 checksum of the asset |
| `mime_type` | string | Yes | Official MIME type |
| `created_at` | string | Yes | ISO 8601 UTC timestamp |
| `alt_text` | string | No | Accessibility alt text (required for images) |
| `license_ref` | string | No | Reference to license in `metadata.json` |
| `tags` | array | No | Arbitrary string tags for organization |

## 4. Supported Asset Formats

### 4.1 Images

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| WebP | `image/webp` | Preferred | Best compression/quality ratio |
| AVIF | `image/avif` | Supported | Next-generation, excellent compression |
| PNG | `image/png` | Supported | Lossless, use for diagrams/screenshots |
| JPEG | `image/jpeg` | Supported | Legacy compatibility |
| GIF | `image/gif` | Supported | Animated only; prefer WebP for static |
| SVG | `image/svg+xml` | Supported | Stored in `assets/images/` as raster-equivalent |

**Recommendation:** Authors should prefer WebP for photographs and AVIF for high-quality images. PNG for lossless content. SVG for interactive vector content should be stored in `assets/vector/`.

### 4.2 Audio

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| OPUS | `audio/ogg; codecs=opus` | Preferred | Best quality/size, open standard |
| AAC | `audio/aac` | Supported | Wide hardware support |
| MP3 | `audio/mpeg` | Supported | Legacy compatibility |
| FLAC | `audio/flac` | Supported | Lossless audio |
| WAV | `audio/wav` | Limited | Only for clips < 1 MB |

### 4.3 Video

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| WebM (AV1) | `video/webm; codecs=av1` | Preferred | Open standard, excellent compression |
| WebM (VP9) | `video/webm; codecs=vp9` | Supported | Open standard |
| MP4 (H.265) | `video/mp4; codecs=hvc1` | Supported | Wide hardware support |
| MP4 (H.264) | `video/mp4; codecs=avc1` | Supported | Maximum compatibility |

Raw uncompressed video is not permitted.

### 4.4 Fonts

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| WOFF2 | `font/woff2` | Preferred | Best compression, modern standard |
| WOFF | `font/woff` | Supported | Legacy compatibility |
| TTF | `font/ttf` | Limited | Only if WOFF2 unavailable |
| OTF | `font/otf` | Limited | Only if WOFF2 unavailable |

Font subsetting is strongly recommended to reduce file size. Only glyphs used in the document should be embedded.

### 4.5 Vector Graphics

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| SVG 1.1 | `image/svg+xml` | Preferred | Open standard, scalable |
| SVG 2.0 | `image/svg+xml` | Supported | Future-ready |

SVG files must be sanitized before embedding — all `<script>` tags and event handlers must be removed. Interactive SVG behavior is implemented through the LDFX script system, not inline SVG scripts.

### 4.6 3D Objects

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| GLB | `model/gltf-binary` | Preferred | Self-contained binary glTF |
| glTF | `model/gltf+json` | Supported | JSON-based, references external files |
| USDZ | `model/vnd.usdz+zip` | Future | Apple ecosystem |

GLB is preferred because it is self-contained — all textures and geometry are in a single file, consistent with the LDFX self-contained document principle.

### 4.7 Structured Data

| Format | MIME Type | Status | Notes |
|---|---|---|---|
| JSON | `application/json` | Preferred | Charts, tables, datasets |
| CSV | `text/csv` | Supported | Tabular data |
| Parquet | `application/vnd.apache.parquet` | Supported | Large datasets |

## 5. Asset Referencing

Pages and scripts reference assets by UUID, not by path. The runtime resolves UUIDs to paths via the asset index.

**Reference format in page content:**
```json
{
  "type": "image",
  "asset_id": "asset-uuid-v4",
  "alt": "Description of the image",
  "width": 800,
  "height": 600
}
```

This decouples page content from asset storage paths. If an asset is re-encoded or renamed, only the asset index needs updating — page content remains unchanged.

---

## 6. Asset Deduplication

Because assets are named by content hash, identical assets are automatically deduplicated:

- If the same image appears on 10 pages, it is stored once in `assets/images/`
- All 10 page references point to the same UUID
- The UUID maps to the single stored file

The runtime must enforce this: when an asset is added to a document, the editor must check if an asset with the same content hash already exists before creating a new entry.

---

## 7. Asset Lifecycle

### 7.1 Adding an Asset

1. Compute SHA-256 hash of the asset bytes
2. Check if an asset with this hash already exists in the index
3. If exists: reuse the existing UUID
4. If not exists: generate a new UUID v4, store the file as `<hash32>.<ext>`, add to index
5. Update `security/hashes.json`
6. Update `manifest.json` feature flags if needed

### 7.2 Removing an Asset

1. Verify no page or script references the asset UUID
2. Remove the asset file from the ZIP
3. Remove the asset entry from `assets/index.json`
4. Update `security/hashes.json`

### 7.3 Orphan Detection

An orphaned asset is one present in `assets/index.json` but not referenced by any page or script.

Orphan detection runs during document save. Orphaned assets generate a warning (Module 08 Stage 8). Repair mode moves orphaned assets to `_orphaned/` for user review.

## 8. Asset Size Limits

| Asset Type | Recommended Max | Hard Limit |
|---|---|---|
| Single image | 50 MB | None (ZIP64) |
| Single audio | 500 MB | None (ZIP64) |
| Single video | 2 GB | None (ZIP64) |
| Single font | 10 MB | None |
| Single 3D object | 500 MB | None (ZIP64) |
| Single data file | 100 MB | None |
| Total `assets/` | No limit | None (ZIP64) |

Exceeding recommended limits generates a performance warning (Module 08 Stage 14).

---

## 9. Asset Integrity

Every asset in `assets/index.json` must have a corresponding entry in `security/hashes.json` (Module 09 §5.2).

The checksum in `assets/index.json` is the full 64-character SHA-256 hex string. The filename uses only the first 32 characters for brevity.

Hash verification is performed in Stage 7 of validation (Module 08 §4).

---

## 10. Accessibility Requirements

| Asset Type | Accessibility Requirement |
|---|---|
| Images | `alt_text` field required in asset index |
| Audio | Transcript or caption file required |
| Video | Caption track required (`has_captions` in metadata) |
| 3D objects | Text description required |
| Charts/data | Data table alternative required |

Documents claiming `wcag_level: AA` or higher must satisfy all accessibility requirements for all assets.

---

## 11. Validation Rules

| Rule | Severity | Condition |
|---|---|---|
| `assets/index.json` missing when assets present | Fatal | Assets folder exists but no index |
| Asset file missing | Fatal | Index entry references non-existent file |
| Asset checksum mismatch | Fatal | Computed hash ≠ declared hash |
| Asset in wrong subdirectory | Warning | Type mismatch with subdirectory |
| Orphaned asset | Warning | Asset not referenced by any page |
| Image missing alt_text | Warning | Accessibility requirement |
| Video missing captions | Warning | Accessibility requirement |
| Font not WOFF2 | Info | Recommend conversion |
| SVG contains script tags | Fatal | Security violation |
| Asset name not content-addressed | Warning | Should follow hash naming convention |
| Duplicate asset content | Warning | Same hash, different UUID — deduplication missed |

## 12. Consistency with Previous Modules

- Assets stored in `assets/` subdirectories as defined in Module 04 §2.3
- Asset compression strategy per Module 03 §8.1 (images/audio/video use Store, others use Deflate)
- Asset checksums included in `security/hashes.json` per Module 09 §5.2
- Asset validation is Stage 8 of the validation pipeline per Module 08 §4
- Feature flags `HAS_VIDEO`, `HAS_AUDIO`, `HAS_3D` in binary header (Module 02 §4) must be set when corresponding asset types are present
- All JSON files use UTF-8 without BOM per Module 01 §4
- SVG sanitization rule is consistent with Module 09 sandbox security model
